### 1. ETL-пайплайн и система мониторинга метрик

**Папка:** [`projects/01_etl_metrics`](projects/01_etl_metrics/)

**Задача:**  
Автоматизировать ежедневный расчёт ключевых пользовательских метрик (DAU, просмотры, лайки, CTR, сообщения) и настроить систему оповещения об аномалиях.

**Технологии:**  
Airflow, Python (pandas, pandahouse, matplotlib), ClickHouse, Telegram Bot API.

**Результаты:**
- Время ручной подготовки отчётов сократилось с 10+ часов до 1 часа в неделю.
- Разработан дашборд для вывода KPI по менеджерам – ускорил принятие решений на 2–3 недели.
- Система алертов на основе статистических доверительных интервалов (z-оценка) позволяет оперативно реагировать на падения метрик.

### 2. A/B-тестирование алгоритма рекомендаций

**Папка:** [`projects/02_ab_test`](projects/02_ab_test/)

**Задача:**  
Оценить влияние нового алгоритма рекомендаций на CTR пользователей и принять решение о раскатке.

**Технологии:**  
Python (pandas, scipy, matplotlib, seaborn), Jupyter, ClickHouse.

**Результаты:**
- Выявлено бимодальное распределение CTR в тестовой группе – алгоритм поляризует аудиторию.
- Глобальный CTR упал на **4.5%** (0.2097 → 0.2003).
- Бакетные тесты и Манна-Уитни дали p-value < 1e-8 – падение статистически значимо.
- **Решение:** не раскатывать алгоритм; провести пост-мортем и вернуть контроль.

### 3. Расчёт размера выборки и MDE

**Папка:** [`projects/03_sample_size_mde`](projects/03_sample_size_mde/)

**Задача:**  
Определить, достаточно ли текущей аудитории для обнаружения ожидаемого эффекта с мощностью 80%.

**Технологии:**  
Python (numpy, pandas, scipy), Jupyter, ClickHouse.

**Результаты:**
- Для порога 50 просмотров мощность составила ~26%, для порога 30 – ~42%.
- Увеличение выборки до 30 600 дало ~56% мощности.
- Фильтрация неактивных пользователей (views ≥ 30) дала ~64% мощности.
- **Вывод:** мощность не достигает 80% – необходимо увеличивать эффект, длительность эксперимента или применять методы снижения дисперсии (стратификация, CUPED).

### 4. Прогнозирование нагрузки на 30 дней

**Папка:** [`projects/04_forecasting`](projects/04_forecasting/)

**Задача:**  
Спрогнозировать общее количество действий (total_actions) на 30 дней вперёд для планирования серверных мощностей.

**Технологии:**  
Python (pandas, numpy, matplotlib), Orbit (модель LGT), ClickHouse.

**Результаты:**
- Модель LGT с недельной сезонностью и регрессором на флешмоб показала **SMAPE = 17.1%** на 7-дневном бэктесте.
- Прогноз успешно отделяет органический тренд от аномального всплеска.
- Верхняя граница 95% интервала – ориентир для пиковой нагрузки.
- Наиболее точны прогнозы на первые 7–14 дней.
